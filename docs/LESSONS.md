# 经验与教训：整套方案落地过程中真实踩过的坑

> 本文记录本方案在实机上部署、调试、长期运行两天里**真实发生**的问题。
> 每条按「现象 → 根因 → 正确姿势」组织。它们大多是"没有报错的静默失败"——
> 这类问题靠文档不存在，只能靠纪律：**每一次变更后都验证，每一次异常都拉证据**。

---

## 一、排查纪律（方法论，比任何单个坑都重要）

### 1. "服务在运行"≠"功能在生效"
- **现象**：`openclash status` 显示 running、进程存在、DNS 劫持规则在位，但流量根本没进代理。
- **根因**：启动脚本中途被打断，clash 进程起来了，但 TCP 透明重定向规则还没装。
- **正确姿势**：验证要看三层——进程在、**防火墙规则在**（`iptables -t mangle -S | grep openclash`）、**日志里有匹配记录**（`grep "using" /tmp/openclash.log`）。UA3F 同理：`ps w | grep ua3f` 看实际启动参数（`-x/-r/-f` 三个值决定一切）。

### 2. 出问题先拉证据，不要先重启
- **现象**：任何一次掉线。
- **教训**：clash 连接日志、ua3f 运行参数都在内存/tmpfs，**重启即销毁**。两次真实掉线的定性（物理断线 vs 封禁）全靠事后日志才分清。
- **正确姿势**：掉线时按固定清单取证——认证日志、冷却标记、链路状态、进程参数、防火墙规则——然后再动手。

### 3. 一次只改一个变量
- **现象**：想把所有对策一次堆上。
- **教训**：堆上去之后如果还被检测，你不知道哪个没用；如果不检测，你不知道哪个起了效。
- **正确姿势**：见 `TEST-PLAN.md` 的分阶段对照实验。本项目实测：TTL/NTP/DNS 全部在位时仍触发检测 → 唯独 UA 没统一 → 锁定 UA 向量。这就是单变量法力的证据。

### 4. 区分三类故障，处置完全不同
| 类别 | 特征 | 处置 |
|---|---|---|
| 对策失效 | 部署完好仍触发检测 | 进入下一阶段实验 |
| 部署回退 | UA3F 没监听/规则丢失 | 修部署，**该次数据作废** |
| 环境问题 | 物理断线、套餐到期 | 与方案无关，别误判 |

### 5. 破坏性/断网操作先告知
- **现象**：验收时主动重启路由器，用户经历 1–2 分钟断网后才被解释。
- **正确姿势**：重启、防火墙重载、接口变更这类操作，先声明影响窗口再执行。

## 二、UA3F 的坑

### 6. 新旧版本配置格式不兼容，且**静默失败**
- **现象**：流量明明进了 UA3F（clash 日志确认），但 UA 原样出来，无任何报错。
- **根因**：路由器装的是 3.6.0 二进制 + 配套 init，而配置是视频教程的 2.3.0 格式（`rewrite_rules` JSON）。init 只认 `ua`/`ua_regex`/`rewrite_mode` 等新选项，旧 JSON 被无视，进程以 `-x RULE -r ''`（规则模式+零规则）启动——**规则模式下空规则集 = 什么都不改写**。
- **正确姿势**：配置必须匹配 init 的 schema（见 `docs/ua3f-config.example`）；装完后用 `ps w | grep ua3f` 核对实际参数；用路由器本机 `curl --socks5-hostname 127.0.0.1:1080 http://httpbin.org/user-agent` 做隔离测试，先证明 UA3F 自己会改写，再排查代理链。

### 7. 改 UA 没生效的第二层：策略与参数
- **教训**：`-x RULE` + 空 `-r` = 不改写；`-x GLOBAL` + `-f <UA>` = 全部改写为该 UA。
- **正确姿势**：统一 UA 选一条**真实的浏览器 UA**（如 Chrome/133 Windows），比统一成 `FFF` 之类的怪值更不显眼；并且让认证脚本的 UA 与之**保持一致**，避免同一出口出现两个 Chrome 版本。

### 8. 开机自启缺失是"时好时坏"的根源
- **现象**：手动跑 UA3F 一切正常，路由器重启后 1080 无监听，此时启动 OpenClash 即全网断。
- **正确姿势**：`/etc/init.d/ua3f enable`；任何情况下**先确认 1080 在监听，再动 OpenClash**。脚本化这个顺序（见 `bootstrap-stack.sh`）。

### 9. 别用 `od`——stock OpenWrt 没有
- **现象**：AES 密钥转 hex 用了 `od`，在真机上不可用。
- **正确姿势**：busybox 环境的等价实现用 awk 的 ord 表（仓库 `proto-gportal.sh` 里有现成的）。

### 10. UA3F 的 ipk 依赖是按 NFQUEUE 模式声明的
- **现象**：`opkg install` 报 `iptables-mod-nfqueue` 依赖无法满足。
- **根因**：SOCKS5 模式根本用不到 NFQUEUE，但 ipk 元数据声明了依赖。
- **正确姿势**：`--force-depends` 安装后验证 1080；或者干脆在"1080 已监听"时跳过安装（幂等设计）。

## 三、OpenClash 的坑

### 11. `MATCH,ua3f` 全量代理是定时炸弹
- **现象**：视频教程的配置把所有 TCP 塞给本地 SOCKS5；UA3F 一挂，全部下游流量涌向不存在的端口，全网断。
- **正确姿势**：只有明文 HTTP（TCP 80）需要统一 UA——TLS 流量检测方本来就看不见 UA。规则改为 `DST-PORT,80,ua3f` + `MATCH,DIRECT`，UA3F 挂掉只影响 http 网页。门户与私有网段规则必须放在最前。

### 12. OpenClash 有两个"开关"
- **现象**：`/etc/init.d/openclash start` 报 `OpenClash Now Disabled`。
- **根因**：init 脚本的 enable（开机自启）和 uci 的 `openclash.config.enable`（功能总开关）是两回事。
- **正确姿势**：两个都要设。 LuCI 里点了"启动"通常只动了后者。

### 13. OpenClash 自管端口
- **现象**：yaml 里写 `mixed-port: 7890`，实际监听 7891/7892/7893/7895。
- **正确姿势**：OpenClash 会按运行模式重写端口，验证时以 `netstat -lnp` 实际输出为准，别迷信 yaml。

## 四、门户行为：错误消息会骗人

### 14. `reasoncode:27 "密码错误，需要重新登录!"` 是个筐
- **现象**：同一报错，一次是**密码大小写打错**（具体值已隐去），一次是**套餐到期**。
- **教训**：门户把多种认证失败都包装成同一条消息。看到它先核对两件事：凭据逐字符核对（大小写！）、账号套餐状态。
- **正确姿势**：改完凭据后 `uci -q get campus-auth.config.password` 与预期**逐字符比对**（比对布尔值，别回显）；套餐问题只能续费/换号。

### 15. `reasoncode:55` 是服务端打标，不是登录失败
- **现象**：登录响应带 55，含义是"检测到共享，关闭并等 15 分钟"。
- **正确姿势**：写冷却标记、暂停一切自动登录（连 LuCI 按钮都应拒绝）；15 分钟后手动重试**一次**。反复重试会被认为对抗处理。
- **重要推论**：认证脚本必须直连门户（`--noproxy` + 绑定 WAN 口 + 私网直连规则），否则门户看到的 UA/特征被代理污染，反而更容易触发 55。

### 16. 登录成功后紧跟的"操作过于频繁"拒绝是无害的
- **现象**：成功登录 2 秒后出现一条被拒记录（门户限频 5 秒）。
- **根因**：自动登录成功后，人工又在 LuCI 点了一次按钮。
- **正确姿势**：在线状态下**不要**再点 Authenticate now——重复登录没有意义还会触发限频。

### 17. 会话跟着 IP 走
- **实测**：路由器重启（WAN 短暂消失）后门户会话存活，恢复通电即在线，无需重新认证；但 WAN 口换了 IP 就会掉。
- **正确姿势**：认证状态查询以门户接口为准（`authState:2/1`），不要用公网 204 探测替代——captive portal 会应答探测，探测失败也不代表账号离线。

## 五、校园网环境的坑

### 18. 共享网段里 ping 不是身份证明
- **现象**：路由器 WAN 释放了 IP 后，ping 原 IP 仍通——那是拿到该 IP 的**别的设备**。
- **正确姿势**：判断路由器在线要看链路状态（`ip link`）+ 门户状态，不要用 ping 网段内地址。

### 19. 校园网访问 GitHub 会间歇性 TLS 重置
- **现象**：curl 交替出现 `HTTP/2 stream not closed cleanly`、`SSL_ERROR_SYSCALL`，重试时好时坏。
- **正确姿势**：下载加 `--http1.1` + 重试；重要安装包**预置到 /tmp**（引导脚本的离线兜底路径）再跑；GitHub API 匿名限额 60 次/小时/IP，脚本里省着用。

### 20. GitHub Releases 的资产列表藏在 `expanded_assets` 里
- **现象**：抓 `releases/latest` 主页 HTML 找不到资产链接；拼出的下载 URL 缺仓库路径而 404。
- **正确姿势**：两步——先从主页抓 `expanded_assets/vX.Y.Z` 的 tag，再抓 `releases/expanded_assets/<tag>` 拿完整 `/owner/repo/releases/download/...` 路径。或者用 API 的 `browser_download_url`。

## 六、工程习惯

### 21. 幂等脚本绝不能覆写凭据
- **现象**：引导脚本在已配置的路由器上重跑（幂等测试），把 UCI 里的真实密码冲成了测试占位符；门户踢线后自动登录拿着假密码被拒，排障方向被严重带偏。
- **正确姿势**：已有非空凭据一律保留，覆写必须显式 `FORCE_CREDS=1`（仓库 `bootstrap-stack.sh` 已实现）。写凭据的验证只比对布尔/长度，**永远不回显**。

### 22. opkg 升级会保留 conffile
- **现象**：升级后新配置选项不生效。
- **根因**：`/etc/config/*` 是 conffile，升级时旧文件保留、新默认放在 `-opkg` 后缀文件里。
- **正确姿势**：升级后合并新选项（uci set）或对比 `-opkg` 文件；写凭据/改配置后记得 `chmod 600`（`uci commit` 可能重置权限）。

### 23. 每次发布都要对齐三处版本
- Makefile 的 `PKG_VERSION/PKG_RELEASE`、本地打包脚本、GitHub tag——三者不一致会让"实机版本"和"Release 版本"对不上号，排障时浪费时间。

### 24. 证据要落在持久层
- 认证日志写到 `/var/log/campus-auth.log`（tmpfs，重启丢失但日常存活），临时状态写在 `/tmp`。**排障前提是不重启**；需要长期保留的证据及时拷出路由器。

### 25. 门户绑定的是"账号×位置"，搬网口 = 新设备；恢复渠道有两个
- **现象**：路由器在 A 宿舍网口长期自动登录正常；断电搬到 B 宿舍网口后，B 位置的电脑用同一账号登录被拒（"绑定次数已用完"）；把路由器搬回 A 原网口，**同样**被拒——来回两次搬家把配额彻底烧光，且一天后仍未自行恢复。
- **根因**：门户的"设备绑定"实际按**账号×物理位置（网口/IP 段）**计数。换网口登录 = 新绑定 = 消耗配额；已绑定的位置掉线重连则只是复用，不消耗。
- **恢复渠道（实测两个）**：
  1. **学校 app 里的"增加绑定"**——不用解绑，直接扩充绑定名额，立刻可用（作者实测恢复）；
  2. **reasoncode:43 自动换绑**——配额耗尽但旧绑定属于路由器自己时，门户会发"是否重新绑定至当前设备"提议（附 bindmac），确认后原绑定挪到当前位置，其他设备不受影响（插件 v1.0.10 已自动化：仅当 bindmac 等于本机 MAC 才接受）；
   **v1.0.13-r13 起的主动变体**：收到 reasoncode:7（次数用完）时插件不再只报错，而是**主动发起"自己换绑给自己"**（reBindMac 填本机 MAC）——换绑是"移动"既有绑定，实测可不消耗次数。若门户接受则自动重新认证，恢复全自动；若拒绝则按原样报错（此时仍需 app）。首次实战验证发生在下一次清晨断网恢复。
- **正确姿势**：路由器固定一个网口别搬；配额烧光先试 app"增加绑定"；报 reasoncode:43 时若 bindmac 是本机可放心自动换绑。脚本侧配套"省配额"策略（夜间静默、失败退避、今日暂停）把重试消耗压到最低。**注意断网时间表不是铁律**：通常每晚 12 点断、早 6 点恢复，但周末晚上可能不断网——恢复策略别按固定时刻表写死。
- **断网形态实测（2026-09-13 早）**：夜里的"断网"很可能**不是链路层断**——6.1 的 WAN 整夜无任何 ifup/udhcpc 失败（DHCP 续租照常成功），但 06:01 门户查询已是离线态：**被清的是认证会话/上网授权**，6:00 前后门户恢复放行。两种模型（"0–6 点封网" vs "6 点集中清会话"）对插件等价：静默窗口不浪费请求，恢复后第一轮检查即触发重登。当日实录：06:01:48 报离线两次 → 门户提供本机 MAC 换绑 → 自动确认 → 06:02:01 认证成功，全程 2 分钟无人工、复用既有绑定。**"周末晚上不断网"的说法被这次实测证伪**（周六夜会话同样被清）——判断依据以晨间日志为准，别按记忆写死策略。
- **附带的坑**：路由器断电重启后时钟可能慢数小时（无 RTC，sysfixtime 恢复旧值 + 无网无法 NTP），所有按时间调度的逻辑（静默窗口、暂停过期）随之偏移；排障时先 `date` 对表，必要时 `date -s @<epoch>` 手动校正。

### 26. 状态页绝不能内联跑探测链：后台缓存 + 瞬时渲染
- **现象**：老路由器（mipsel_24kc，上行慢）打开运行状态页要卡 5~6 秒，且旧版每 10 秒整页 `meta refresh` 一次，用户看到的大部分时间是白屏；其他 CBI 插件页都没这么慢。
- **根因**：模板渲染时同步 `io.popen` 一串探测——联网检查 `curl -m 6` 在**未认证状态会等满 6 秒超时**，加上 netstat/pgrep/ps/tail 各 fork 一次，全部串行阻塞页面；整页刷新又把主题框架一起重渲染，成本翻倍。
- **正确姿势（v1.0.13 实装）**：
  1. 所有探测搬进 `campus-auth --probe`，结果写 `/tmp/campus-auth.probe` + `/tmp/campus-auth.logtail`（原子写：先 `.new` 再 `mv`）；
  2. 页面只**读缓存**（毫秒级），缓存超过 10 秒就 `os.execute("... --probe ... &")` 后台补一次，本轮先显示旧值或"检测中…"，下一轮轮询拿到新值；
  3. 整页刷新改为 XHR 只刷新状态区块（`/fragment` 端点返回裸片段，不带主题），主题骨架永不重载。
- **实测**：页面内容可见时间从 6 秒+ 降到 25ms；离线时渲染也不再有卡顿。
- **附带的坑**：
  - 老 LuCI 的 tparser 兼容性：`<%-- --%>` 长注释不支持（把 `--` 当 Lua 代码，报 unexpected symbol），要用 `<% --注释 --%>` 的 Lua 注释写法；`<%+` 是 include 保留字；`local a="", b=""` 多变量一行声明不支持，要分开写；
  - 纯 Lua dispatcher 下 `template()` 不自动包主题，必须 `call()` 手动 render header/片段/footer；
  - uhttpd 环境里 spawn 后台任务要用**绝对路径**并重定向 stdin/stdout，否则找不到命令或挂住请求。

### 27. 没有网页密码时调试 LuCI：会话与登录的几个坑
- **坑 1**：`/etc/config/rpcd` 的 `option password` 必须是 **crypt 哈希**（如 `$1$salt$...`，可用 `openssl passwd -1 -salt xx 生成`），写明文永远登录失败（rpcd 直接拿它当 hash 比较）；`$p$root` 表示读系统 shadow。
- **坑 2**：`ubus call session login` 拿到的会话**缺 `token`**，LuCI dispatcher 的 `session_retrieve` 要求 `values.token` 是字符串——还要再 `ubus call session set` 补一个 token，然后把会话 id 设为浏览器的 `sysauth` Cookie 才能进后台。
- **坑 3**：浏览器里残留**两个同名 `sysauth` Cookie**（旧的过期会话 + 新的）时，服务端只读第一个，永远 403；要把 Cookie 在所有 path 变体下删干净再设新的。
- **坑 4**：改 `/etc/shadow` 或 rpcd 配置后立即生效的是**登录路径**，但正在运行的会话在 rpcd 内存里，重启 rpcd 会全掉——调试时先造好新会话再恢复原配置。
- **纪律**：动密码前先备份（`cp /etc/shadow /etc/shadow.bak`），验证完立刻原样恢复；临时哈希/密码用完即弃，**任何真实凭据不进文档、不进仓库**。

### 28. 本地打包清单必须和 Makefile 对表；`[ -x ... ] || skip` 守卫会把缺文件吞掉
- **现象**：反检测模式切过去后 UA3F 没起来、加固没生效，且**没有任何报错**——init 脚本里 `[ -x /usr/bin/campus-auth-mode ] && apply` 的容错守卫把"文件不存在"静默跳过了。
- **根因**：仓库上游 Makefile 安装 `campus-auth-mode.sh`，但本地 `build-ipk.py` 的文件清单漏了它——于是本地打的每个 ipk 都缺这个文件，在依赖 Makefile 安装的老设备上没事，新装/换机的全中招。
- **教训**：
  - 守卫代码是给"可选依赖"用的；**核心组件缺文件必须报错**（apply 脚本开头 `[ -f ... ] || { log "install broken: campus-auth-mode missing"; exit 1; }`），静默降级只留给真正可选项；
  - 每次改打包清单/Makefile 后，做一次"装机后清点"：`opkg files <pkg>` 与源码 `files/` 目录对表；
  - 发布前用一台干净设备（或全新 opkg root）跑一遍模式切换冒烟测试，而不是只在升级过的老环境验证。
- **另一个静默拒绝**：ua3f 安装包默认配置 `ua3f.enabled.enabled=0`（总开关关），init 脚本同样静默不起——重装/覆盖配置后 UA3F 突然"消失"多半是它；装完必须置 1。安装脚本已内置。
- **测试方法备忘（无需账号密码即可验证大半链路）**：`campus-auth --check`（只读门户查询：拉登录页+查认证状态）；空凭据跑 `campus-auth`（应干净退出 exit 1，不发门户请求）；openssl AES 加解密往返；切模式看 UA3F 监听 1080 与加固规则；切回 normal 确认清理。真正需要凭据的只有 authLogin 提交那一步。

### 29. 控制 OpenClash 的三个坑；加固必须热插拔触发
- **坑 1（检测误报）**：`pgrep -f openclash` 会匹配 **ucitrack 守护进程**（命令行带 `-a openclash`）和 init 包装脚本，导致"看起来一直在跑、从来不真正启动"。必须只认核心进程路径：`pgrep -f "/etc/openclash/"`（兼容老布局 `/etc/openclash/clash` 和新布局 `/etc/openclash/core/clash*`）。调试时小心：**你自己 ssh 命令行里含同样字样也会被 pgrep 匹配**，验证时用变量拆词（`PAT="open"; pgrep -f "${PAT}clash/core"`）。
- **坑 2（uci 开关）**：OpenClash 的 init 脚本要求 `openclash.config.enable='1'`，否则打印 "Need Start From Luci Page, Exit" 直接退出。模式管理器启停它时要同步置位/复位这个开关。
- **坑 3（commit 触发重启风暴）**：`uci commit openclash` 会触发 **ucitrack 对 openclash 的自动 restart**——与自己的 start 并发会把对方核心杀掉，表现为"启动成功几秒后无故停止"。对策：值没变就不 commit；start 后轮询等待核心（慢路由要 10 秒以上），不在了自动补一次。
- **加固触发**：上联口往往在切模式之后才就绪（插线晚、校园网 DHCP 慢），限时重试会过期失效。正确做法是 **netifd 热插拔钩子**（`/etc/hotplug.d/iface/` 里 ifup 时后台重跑 mode apply），插线永远自动生效。
- **远程调试守则**：任何"远程 ssh 一条命令"里若包含与脚本内 pgrep 相同的进程名，都会污染脚本自己的检测——先想清楚命令行字符串会被谁看见。

### 30. 多台路由器机队的运维纪律：一键、自检、刷完必优化
- **现象**：逐项手工配置多台路由器时，每台都会漏不同的步骤（UA3F 总开关、`en_mode`、加固触发时机），而且都是事后才发现，返工成本高。
- **纪律（实测有效）**：
  1. **一键刷机**：所有配置进安装脚本，现场零交互；`flash.sh` 上传 → 安装 → 时钟同步 → 清理一条龙；
  2. **验证不过关不下班**：安装器结尾逐项验证（文件清单 / 模式值 / 监听口 / 核心进程 / utun 接口），FAIL 必须显式退出；
  3. **刷完必做全功能自检**：UA 改写实测 + 自愈实测（方法见 README"模式②全功能自检"），别只看进程在不在；
  4. **每次刷完优化一次安装脚本**：当场暴露的小瑕疵（误报警、等待不足）立刻修进脚本，下一台受益；
  5. **设备识别**：同一 IP 轮流插拔多台时 host key 必变（`ssh-keygen -R <ip>` 清旧记录），靠"已装插件版本 + MAC + uptime"识别设备；同时注意 #29 的 pgrep 自匹配。
- **增量部署的坑**：opkg 同版本重装**不会**恢复被删除的 conffile，需要 `--force-reinstall` 或从 ipk 手动 tar 提取；`ua3f.enabled.enabled` 默认为 0，每次重装/换机都要重新置 1。

### 31. 半砖路由器的 PC 侧诊断与 failsafe 救援
- **现象**：路由器 LAN 口灯亮、链路 1Gbps 协商成功，但无 DHCP 应答、无 ARP、无 IPv6 应答，所有候选网段的网关全部 ping 不通。
- **PC 侧免管理员诊断（Windows）**：
  1. **收包节拍分析**：`Get-NetAdapterStatistics`（属性名随系统版本不同，Unicast/Broadcast/Multicast 三项要相加）每秒采样——**每 2~3 秒 1 包、永无变化的"节拍器"**= 交换芯片活着、CPU 不工作（或对端根本是墙口交换机的 BPDU 心跳）；**周期性爆发** = 循环重启；**全零** = 线没插对/对端没电；
  2. **known_hosts 考古**：上次刷机连过的 IP 都留在 `~/.ssh/known_hosts`（哈希条目用 `ssh-keygen -F <ip>` 解码），能直接给出"这台以前叫什么"；
  3. 别信 busybox `pgrep -x` 对短进程名的匹配，用 `ps w | grep` 或 `netstat -tln`；busybox nc 常是阉割版（`nc [IPADDR PORT]`，**没有监听模式**），抓包测试别指望它。
- **UA 改写功能实测（离线可用，不依赖外网）**：在路由器上放一个 uhttpd CGI（`/www/cgi-bin/ua-test` 打印 `HTTP_USER_AGENT`），对比 `curl -x socks5h://127.0.0.1:1080`（应为 Chrome 指纹）与直连（应原样）——比 nc 抓包可靠得多，且能区分"UA3F 没改写"与"改写了但抓包没抓到"。
- **failsafe 救援**：断电 → 按住 RESET → 通电 → LED 快闪（每秒 4~5 次）后松开；路由器固定在 `192.168.1.1`，**无 DHCP**（电脑要配 192.168.1.x 静态 IP），dropbear 免密进入后 `mount_root` 排查或 `firstboot` 重置。**DSA 平台（mt7981 等）failsafe 只监听 LAN1 口**，网线插别的口连不上——"进了 failsafe 还是连不上"先换到 LAN1 再排查。频繁拔电的机器优先怀疑 overlay（JFFS2）损坏。
- **实机案例（2026-09）**：一台路由器呈现完整"节拍器"特征（1Gbps 链路正常、每 2~3 秒 1 包恒定心跳、无 DHCP/ARP/ICMPv6 应答、全候选网段无回应、failsafe 进不去、按住 RESET 重启心跳节奏不变）——最终确认 **CPU 侧硬件故障**，交换芯片独立存活所致，已退换。教训：确认线在 LAN 口且 failsafe（含换 LAN1）都无效后，剩余可能性基本只剩硬件故障，按节拍器特征即可下结论，不必继续在软件层耗时间。
- **沟通**：UAC/授权类系统弹窗必须**提前一句话说明用途**，否则大概率被当成可疑弹窗直接取消。
